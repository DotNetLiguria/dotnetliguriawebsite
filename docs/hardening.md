# Production security and privacy hardening

## Code issues, mitigations and solutions

This section reports the status of the ten findings from the code review
baseline. **All ten baseline findings have been addressed in repository code.**
The severities below are the original review severities, not open findings in
the current code. Deployment-dependent work and unverified existing data are
listed separately under [Publishing potential issues and recommendations](#publishing-potential-issues-and-recommendations).

| # | Baseline severity | Finding at review | Code status | Mitigation and solution |
|---|---|---|---|---|
| 1 | HIGH | OIDC token destination rules could accept lookalike destinations. | **Addressed** | `src/dotnetliguriaspa/public/OidcTrustedDomains.js` restricts destinations to exact approved HTTPS hosts and paths, with a separate HTTPS localhost development exception. The OIDC worker is generated by `scripts/sync-oidc.mjs`. |
| 2 | HIGH | Admin-role matching accepted unscoped roles and loosely truthy privilege values. | **Addressed** | The legacy role/Boolean-claim matchers and their configuration options have been removed. Task policies require exact catalogue entries in the validated `permissions` claim, intersected with current API-client grants. Realm roles, flattened roles and Boolean aliases confer no application access. Regression tests cover legacy-grant rejection and granular authorization; see authorization.md. |
| 3 | MEDIUM | New questionnaire responses could persist respondent PII and email-based deduplication keys. | **Addressed for new submissions** | Authenticated submissions derive issuer/subject from the validated account, use account-based deduplication, and reject submitted respondent PII. Legacy BSON fields remain readable for compatibility; whether old records contain PII is a data-inventory and publishing task, not a remaining new-write defect. |
| 4 | MEDIUM | Submitted respondent identity and username/email author attribution were not trustworthy. | **Addressed for new writes** | The API authenticates bearer submissions and derives account identity from the token principal. Questionnaire author attribution uses the authenticated issuer/subject; client-supplied respondent identity is rejected. Historical records require the separate legacy-data assessment. |
| 5 | MEDIUM | Forwarded headers lacked an explicit trust boundary. | **Addressed in code; runtime values required** | Forwarded-header processing is limited to explicitly configured trusted proxies, with a one-proxy boundary. The production proxy address, network isolation and HTTPS on both hops must be supplied and verified by IT; see the publishing section. |
| 6 | MEDIUM | Wildcard CORS and missing browser-security policies. | **Addressed in code; production configuration required** | CORS validates explicit HTTPS origins; production responses apply CSP and other security headers. The actual production host/origin overrides still need IT validation. |
| 7 | MEDIUM | Backups lacked an erasure lifecycle; snapshot storage protection was unknown. | **Application lifecycle addressed; storage protection is a publishing requirement** | Backup/restore operations share an operation gate, check the privacy epoch and erasure state, and fail closed unless protected storage is approved. Erasure purges application-owned snapshots. Backup permissions are now separated into `backups.read`, `backups.create` and MFA-protected `backups.restore`; see authorization.md. Snapshot files are plaintext JSON; the application does not provide at-rest encryption. IT must protect the storage before approving/enabling it. |
| 8 | MEDIUM | Upload checks relied on extensions and unpublished files could be public. | **Addressed for new uploads** | New uploads use generated names, private storage, content/signature and size checks, and publication-aware downloads. Unpublished assets are not served anonymously. Historical `Contents` assets are retained and must be inventoried for public drafts before release. |
| 9 | LOW | Questionnaire answer drafts could persist indefinitely in the browser. | **Addressed** | Drafts are owner-bound `sessionStorage` entries with a 30-minute inactivity expiry and cleanup on invalidation, discard, logout or account change. |
| 10 | LOW | HTTPS metadata was not required for identity configuration. | **Addressed** | Identity authority and metadata are required to use HTTPS, including runtime validation. |

Additional code controls include bounded request/read sizes and pagination,
public/private API projections, safe structured errors, sensitive `no-store`
responses, upload path containment, privacy-erasure coordination, expiring
unsubscribe capabilities, and publication artifact checks. These controls do
not establish that production configuration or historical data is safe.

### Code TODO summary

**Open code fixes for the ten reviewed baseline findings: none (10/10
addressed).** In particular, the HIGH-severity role authorization issue is
fixed and covered by tests.

The following are intentionally not represented as completed code features:

- No automatic ingestion of externally initiated identity-provider deletions is
  included; administrators must use the documented reconciliation process.
- Email delivery is unavailable until an approved provider and consent-at-send
  controls are configured. The application must not report a campaign as sent
  while delivery is unavailable.
- No automatic anonymizer is claimed for arbitrary free text, and no malware
  scanner is included for uploads. Unsupported office archives are rejected.
- Large-dataset streaming reports are not implemented; bounded operations fail
  explicitly rather than silently returning partial results.

These are deployment/product gates, not unaddressed defects in the ten-item
code review baseline. Do not enable a gated operation to work around a missing
control.

## Publishing potential issues and recommendations

These items depend on production configuration, operational practice or existing
data. They are **not current code findings**, and repository tests cannot verify
them. Coordinate with IT and the data/controller owners before production use.
Detailed procedures and configuration checklists are in
[`security-operations.md`](security-operations.md) and
[`privacy-backend.md`](privacy-backend.md).

| Potential issue | Why it is deployment-dependent | Recommendation for IT / owner |
|---|---|---|
| Proxy trust, host and TLS boundary | The repository cannot know the production NGINX upstream address, network ACLs, certificates or runtime `AllowedHosts`. | Set only the actual NGINX address in `Security:KnownProxies`; restrict backend access to that proxy; enforce and verify HTTPS on both hops; set production hosts to the apex and `www` only; reject unknown Host/SNI names. Do not trust forwarded headers from arbitrary clients. |
| Identity-provider client and role mappings | Live issuer, audience, callback URLs, role assignments, privilege claims and MFA-token claims are configured outside this repository. | Configure the SPA as a public authorization-code client with PKCE S256 and exact callback/logout URLs. Configure backend and administration credentials at runtime. Follow authorization.md: Full Scope Allowed OFF, explicit API role-scope mappings, restricted permissions mapper and reviewed task bundles. Test live revocation and destructive-operation `acr`/`auth_time` with synthetic accounts. |
| Backup and privacy storage | Snapshot JSON and privacy records rely on external at-rest encryption, ACLs, protected Data Protection keys and operational-copy lifecycle. The approval flags are attestations, not encryption. | Keep backup storage outside served/published roots; apply encryption and restrictive ACLs; protect and persist Data Protection keys; document recovery and deletion of operational copies. Keep storage-approval flags false until these controls are independently verified. Do not expose the development/recovery backup capability to general users. |
| Legacy database records and exports | New-write protections do not remove existing respondent PII, email keys, usernames, free text, old snapshots, exports or logs. No production inventory or transition has been run. | Run the read-only inventory with a least-privilege account. Report counts and field paths, not raw values in logs. Assess every collection, unknown/nested fields, backups, downloads and external copies. Obtain separate approval and a reviewed bounded transition before any production writes. Never reconnect an account by matching unverified email. |
| Historical workshop assets | New uploads are private, but historical `Contents` URLs are intentionally preserved and may include previously public draft material. | Inventory historical assets and publication state. Restrict or remove sensitive drafts through an approved process while preserving published workshop assets and URLs. Do not delete historical content blindly. |
| Identity deletion, legal and notification operations | External identity-provider deletion events, retention decisions, controller details and email-provider behavior are outside the running application. | Establish and audit the manual identity-reconciliation process. Obtain controller/legal approval for purposes, retention, contacts and provider locations. Do not enable delivery before provider approval, dispatch-time consent checks, unsubscribe handling and external-copy deletion procedures are demonstrated. |
| Release and runtime verification | Local tests do not prove deployment artifacts, Linux behavior, browser SSO, real database operations or the production proxy boundary. | Run the publish/artifact checks and Linux/Windows CI. Perform opt-in synthetic staging login, MFA, erasure, reconciliation and restore checks. Verify the deployed SPA and API through the actual HTTPS endpoint; do not treat a Vite-only or loopback test as production evidence. |
